## 核心知识点

### TCP vs UDP

面试官想听：连接性、可靠性、有序性、速度四个维度对比 + 一个各自的典型应用。

| 维度 | TCP | UDP |
|---|---|---|
| 连接 | 面向连接（握手挥手） | 无连接，直接发 |
| 可靠性 | 可靠：确认重传、滑动窗口、流量/拥塞控制 | 尽力而为，可能丢包乱序 |
| 数据形态 | 字节流（无消息边界） | 数据报（有边界） |
| 速度/开销 | 头部 20 字节起，握手有延迟 | 头部 8 字节，低延迟 |
| 场景 | HTTP、文件传输、数据库连接 | DNS、视频直播、游戏、心跳广播 |

- TCP 可靠传输三板斧：**确认应答（ACK）+ 超时重传**保证不丢；**序号 + 接收缓冲重排**保证有序；**滑动窗口**限速（流量控制）+ **拥塞控制**（慢启动、拥塞避免）保护网络。

### 三次握手 / 四次挥手

面试官想听：能画出双向确认的过程，并回答「为什么握手是三次、挥手是四次」两个为什么。

- **三次握手（建立连接）**：客户端发 SYN → 服务端回 SYN+ACK → 客户端再回 ACK，连接建立。
- 为什么三次：确认**双方的收发能力都正常**；两次无法让服务端确认「客户端能收到我的包」，同时防止历史（过期）SYN 重复建立连接。
- **四次挥手（断开连接）**：主动方 FIN → 对方 ACK → 对方（数据发完后）FIN → 主动方 ACK，进入 **TIME_WAIT** 等 2MSL 后关闭。
- 为什么四次：TCP 全双工，两个方向的关闭各自独立，ACK 和 FIN（被动方收到 FIN 后可能还有数据要发）不能合并，故 ACK、FIN 分开发送。
- TIME_WAIT 的意义：确保最后的 ACK 若丢失可重传、让旧报文在网络中消亡；大量 TIME_WAIT 常见于短连接服务，可调 `tcp_tw_reuse` 优化。

### HTTP 基础

- 请求报文：请求行（方法 URL 版本）+ 请求头 + 空行 + 请求体；响应报文：状态行 + 响应头 + 响应体。
- 常见状态码：**200 成功、301/302 重定向、400 客户端请求错误、401 未认证、403 禁止、404 未找到、500 服务器内部错误、502 网关错误、504 网关超时**。
- **GET vs POST**：语义上 GET 获取（幂等、参数在 URL、可缓存可收藏）；POST 提交（不幂等、参数在 body）；本质都是 TCP 上的报文，区别是约定而非硬性限制。

### HTTPS 握手概念

- TLS 在 TCP 与 HTTP 之间：① 客户端请求并携带支持的加密套件；② 服务端返回证书；③ 客户端用内置 CA 验证证书，生成随机预主密钥并用**服务端公钥**加密发送；④ 双方据其算出对称密钥，之后用**对称加密**通信。
- 混合加密的原因：非对称加密安全但慢，只用来交换密钥；数据传输用快的对称加密。这一过程同时解决机密性与身份认证（证书）。

### Socket 编程 demo

```java
// 服务端：accept 阻塞等连接，每连接一个线程处理（BIO）
try (ServerSocket server = new ServerSocket(8080)) {
    while (true) {
        Socket socket = server.accept();              // 阻塞点 1
        new Thread(() -> {
            try (BufferedReader in = new BufferedReader(
                     new InputStreamReader(socket.getInputStream()));
                 PrintWriter out = new PrintWriter(socket.getOutputStream(), true)) {
                String line;
                while ((line = in.readLine()) != null) {   // 阻塞点 2
                    out.println("echo: " + line);
                }
            } catch (IOException ignored) { }
        }).start();
    }
}
```

```java
// 客户端
try (Socket s = new Socket("127.0.0.1", 8080);
     PrintWriter out = new PrintWriter(s.getOutputStream(), true)) {
    out.println("hello");
}
```

- UDP：`DatagramSocket` + `DatagramPacket`，`send/receive` 收发数据报，无需连接。
- Java 11 标准 `HttpClient`：支持 HTTP/2、同步 `send` 与异步 `sendAsync`（返回 CompletableFuture）：

```java
// Java 11 标准 HttpClient：支持 HTTP/2、同步 send 与异步 sendAsync
HttpClient client = HttpClient.newHttpClient();
HttpRequest req = HttpRequest.newBuilder(URI.create("http://localhost:8080/api/health")).build();
HttpResponse<String> resp = client.send(req, HttpResponse.BodyHandlers.ofString());  // 同步
client.sendAsync(req, HttpResponse.BodyHandlers.ofString())
      .thenApply(HttpResponse::body)                                                  // 异步
      .thenAccept(System.out::println);
```

### BIO / NIO / AIO 对比

面试官想听：用「等谁」来区分——BIO 等数据、NIO 等就绪事件、AIO 等完成通知；再补连接数与线程数的关系。

| 模型 | 全称 | 阻塞点 | 线程模型 | 适用 |
|---|---|---|---|---|
| BIO | 同步阻塞 | accept/read/write 全阻塞 | 一个连接一个线程 | 连接少且固定 |
| NIO | 同步非阻塞 | 线程轮询 Selector 等就绪事件 | 一个线程管理多个 Channel | 连接多、请求轻（高并发核心） |
| AIO | 异步非阻塞 | 发起后立即返回，完成后回调 | 系统完成 I/O 再通知 | 理论最优，Linux 实现不成熟，实际少用 |

- 记忆口径：BIO/NIO/AIO 的本质差异在「等待阶段用户线程做不做事」：BIO 死等、NIO 不阻塞但需主动轮询事件、AIO 注册回调由内核完成。
- 「同步/异步」看**是谁完成真正的 I/O 拷贝**（用户进程 = 同步，内核通知 = 异步）；「阻塞/非阻塞」看**发起调用后线程是否挂起**。

### NIO 三大件：Channel / Buffer / Selector

面试官想听：能讲一个完整事件循环：注册 → select 轮询 → 判断事件类型 → 读写，并注意 flip。

- **Channel（通道）**：双向数据通道（Stream 是单向的），`SocketChannel/ServerSocketChannel/FileChannel`，配合 Buffer 读写。
- **Buffer（缓冲区）**：`ByteBuffer` 核心参数 `position/limit/capacity`；写完读之前必须 `flip()`（limit 置为 position、position 归零），`clear()` 重写、`rewind()` 重读。
- **Selector（多路复用器）**：一个线程注册多个 Channel，`select()` 阻塞到任一 Channel 就绪，返回 `SelectionKey` 集合（OP_ACCEPT/OP_READ/OP_WRITE/OP_CONNECT），就绪才分配线程读写——把「每连接一线程」变成「每就绪事件一处理」。

```java
Selector selector = Selector.open();
ServerSocketChannel ssc = ServerSocketChannel.open();
ssc.configureBlocking(false);                      // NIO 必须非阻塞
ssc.register(selector, SelectionKey.OP_ACCEPT);
while (selector.select() > 0) {                    // 轮询就绪事件
    for (SelectionKey key : selector.selectedKeys()) {
        if (key.isAcceptable()) ((ServerSocketChannel) key.channel()).accept();
        // ... 处理 OP_READ 等，处理后 remove key
    }
}
```

- 多路复用底层：**select**（fd 数组遍历，1024 上限）、**poll**（链表，无上限但仍 O(n) 遍历）、**epoll**（红黑树 + 就绪链表 + 事件回调，O(1)，Linux 2.6+，Netty/Nginx 依赖它）。一句话：**select/poll 是遍历所有 fd 问谁好了，epoll 是内核把好的 fd 主动报给你**。

### Reactor 模式

- 核心思想：**I/O 多路复用 + 事件分发**——Reactor 线程监听事件，分发给 Handler 处理。
- 单 Reactor 单线程（Redis 6 前）、单 Reactor 多线程（工作线程池处理业务）、主从 Reactor 多线程（accept 由主 Reactor，I/O 由子 Reactor 组）——Netty 默认主从模式（bossGroup + workerGroup）。

### 零拷贝

面试官想听：传统读发要 4 次拷贝 4 次上下文切换，mmap/sendfile 把它降到 2 次甚至 0 次 CPU 拷贝。

- 传统方式 `read + write`：磁盘 → 内核缓冲 → 用户缓冲（应用）→ Socket 缓冲 → 网卡，**4 次拷贝、4 次用户态内核态切换**。
- `mmap`（内存映射）：用户空间与内核缓冲共享映射，减少一次拷贝；`sendfile`：数据直接在内核内从文件缓冲流向 Socket 缓冲，用户态零参与；网卡支持 gather 时连 Socket 缓冲拷贝都省掉（DMA 直接收集），仅 2 次拷贝且全在内核。
- Java 对应：`FileChannel.transferTo()` 即 sendfile；Kafka 高吞吐、RocketMQ、Nginx `sendfile on` 都是受益者。**适用条件：不需要在应用层修改数据**，需要加工时仍要走用户态。

### Netty 定位与为什么快

面试官想听：Netty = 封装好 NIO 的异步事件驱动网络框架，快在四点：Reactor 线程模型、epoll、零拷贝、池化内存。

- 定位：屏蔽 JDK NIO 复杂 API 与空轮询 bug（epoll bug），提供统一的异步事件驱动编程模型；Dubbo/gRPC/ElasticSearch 等的通信底座。
- 高性能四要点：① **主从 Reactor 多线程模型**（boss 收连接、worker 处理 I/O）；② 基于 **epoll** 多路复用；③ **ByteBuf 池化**（PooledByteBufAllocator，减少 GC）与 CompositeByteBuf 等零拷贝（逻辑组合而非物理拷贝）；④ **无锁串行化设计**——消息在同一个 Channel 上始终由同一线程处理，避免锁竞争。
- 组件速记：`Channel`（连接）、`EventLoop/EventLoopGroup`（线程+多路复用循环）、`ChannelPipeline`（Handler 责任链，解码/业务/编码）、`ByteBuf`（增强 Buffer）。

## 高频面试题

**Q：说说 TCP 三次握手和四次挥手。⭐**
- 握手：SYN → SYN+ACK → ACK；目的是确认双方收发能力、同步初始序列号、防止历史连接误建。
- 挥手：FIN → ACK → FIN → ACK；因 TCP 全双工，被动方 ACK 与 FIN 不能合并（可能还有数据要发）。
- 主动方最后进入 TIME_WAIT 等 2MSL：保证最后的 ACK 丢失可重传、旧报文自然消亡。

**Q：为什么握手是三次而不是两次？**
- 两次时服务端无法确认「客户端能收到自己的包」，连接的发送通道未获确认。
- 同时无法阻止一个在网络中滞留的旧 SYN 再次建立无效连接。
- 三次是确认双方收发能力的最小次数。

**Q：TCP 如何保证可靠传输？**
- 序号 + 确认应答（ACK），超时或收到重复 ACK 触发重传。
- 接收缓冲区对乱序数据重排。
- 滑动窗口做流量控制（不压垮接收方），慢启动/拥塞避免做拥塞控制（不压垮网络）；校验和检查数据损坏。

**Q：BIO、NIO、AIO 的区别？⭐**
- BIO 同步阻塞：accept/read 全阻塞，一个连接一线程，连接多时线程暴涨。
- NIO 同步非阻塞：Selector 多路复用，一个线程监听多个 Channel 的就绪事件，就绪才读写；「同步」指数据拷贝仍由用户线程发起完成。
- AIO 异步非阻塞：发起后立即返回，内核完成 I/O 后回调通知；Linux 实现不成熟，实际生产多用 NIO。
- 一句话：BIO 等数据、NIO 等事件、AIO 等通知。

**Q：select、poll、epoll 的区别？一句话概括。**
- select：固定大小 fd 数组，每次全量遍历 O(n)，有 1024 上限。
- poll：链表突破数量上限，但仍 O(n) 拷贝与遍历。
- epoll：红黑树管理 fd + 就绪链表回调，只返回就绪的 fd，O(1)；一句话——前两者是「挨个问谁好了」，epoll 是「好了的主动排队」。

**Q：什么是零拷贝？⭐**
- 传统 read+write：4 次拷贝（磁盘→内核缓冲→用户缓冲→Socket 缓冲→网卡）+ 4 次上下文切换。
- sendfile 让数据全程在内核态流转，CPU 拷贝降为 0~1 次、切换降为 2 次；mmap 用映射减少一次拷贝。
- Java 里 `FileChannel.transferTo` 即 sendfile；Kafka/RocketMQ/Nginx 借此实现高吞吐；前提是应用不需要改数据。

**Q：Netty 为什么高性能？⭐**
- 主从 Reactor 多线程模型：bossGroup 收连接，workerGroup 处理 I/O，业务不阻塞 I/O 线程。
- 底层基于 epoll 等 I/O 多路复用，并修复了 JDK NIO 的空轮询 bug。
- ByteBuf 池化 + 复合缓冲的零拷贝，减少内存分配与 GC。
- 单 Channel 事件无锁串行化到同一 EventLoop，避免锁竞争；pipeline 责任链灵活编解码。

**Q：HTTP 常见状态码？GET 和 POST 的区别？**
- 2xx 成功、301/302 重定向、400 参数错误、401 未认证、403 无权限、404 不存在、500 服务器错误、502/504 网关错误。
- GET 获取资源：幂等、参数在 URL、可缓存；POST 提交数据：参数在 body、一般不幂等。
- 面试加分：安全层面 GET 会被浏览器历史/日志记录，敏感数据应用 POST + HTTPS。
