### 1.（Java基础·易）JDK、JRE、JVM 三者的包含关系是？
- A. JDK ⊃ JRE ⊃ JVM
- B. JVM ⊃ JRE ⊃ JDK
- C. JRE ⊃ JDK ⊃ JVM
- D. 三者互相独立

答案：A
解析：JDK = 开发工具 + JRE，JRE = JVM + 核心类库；只需运行程序装 JRE，要开发才装 JDK。详见[《01-环境搭建与基础语法》](/java-study-guide/posts/01-环境搭建与基础语法/)

### 2.（Java基础·中）`StringBuilder sb = new StringBuilder("a");` 调用 `change(sb)`，方法体为 `void change(StringBuilder x){ x.append("b"); x = new StringBuilder("c"); }`，之后 sb 的内容是？
- A. a
- B. c
- C. ab
- D. bc

答案：C
解析：Java 只有值传递：append 修改的是同一个对象，而重新赋值只改变了形参的指向，不影响实参。详见[《01-环境搭建与基础语法》](/java-study-guide/posts/01-环境搭建与基础语法/)

### 3.（Java基础·易）`Integer a = 127, b = 127; System.out.println(a == b);` 输出什么？
- A. false
- B. 编译错误
- C. 不确定
- D. true

答案：D
解析：IntegerCache 缓存 -128~127，范围内 == 比较的是同一个缓存对象；超出范围（如 128）必须用 equals。详见[《02-面向对象与核心类》](/java-study-guide/posts/02-面向对象与核心类/)

### 7.（集合·中）JDK 1.8 中 ArrayList 首次 add 时容量扩到 10，此后每次扩容为原来的？

- B. 1.2 倍
- C. 3 倍

答案：D

### 8.（集合·中）HashMap（JDK 1.8）中链表转红黑树的条件是？

### 14.（并发·中）线程池提交任务后的处理顺序是？

答案：C

- B. 频繁 rebalance 只影响新加入的消费者，组内其他消费者不受影响

- D. [{ $group: { _id: "$brand", count: { $sum: 1 } } }, { $sort: { count: -1 } }, { $match: { price: { $gte: 1000 } } }]

答案：A
解析：聚合管道严格按数组顺序执行。$match 越靠前越能先滤掉无关文档、大幅减少后续阶段的数据量（还能利用索引），$group 做分组聚合，$sort 最后对聚合结果排序。B、D 在 $group 之后才过滤，等于白算了一大批文档；C 里 $sort 的 count 字段此时根本不存在。详见[《08-MongoDB》](/java-study-guide/posts/08-MongoDB/)

答案：C
解析：JWT 的无状态是用"吊销难"换来的：服务端不存会话，只能等它自然过期。务实做法是缩短 Access Token 寿命、把长期凭证换成存库可吊销的 Refresh Token，再用 Redis 黑名单兜底；B 等于把 JWT 用回了 Session，D 毫无作用——token 仍然有效。详见[《06-认证与安全》](/java-study-guide/posts/06-认证与安全/)

### 266.（分布式与高并发·易）关于 MySQL 读写分离，下列说法正确的是？

### 268.（分布式与高并发·易）缓存集群从 3 个节点扩到 4 个，运维只改了应用里的取模基数，随后数据库压力陡增。最直接的原因是？

- B. 新节点上的槽位需要时间预热，预热期间读请求会穿透到数据库
- C. 客户端没有预热，冷启动必然打满数据库
- D. 4 个节点无法组成集群，必须使用奇数节点

解析：`hash(key) % N` 的落点与 N 强绑定，N 从 3 变 4 时只有极少数 key 恰好落回原节点，等于整层缓存被清空。一致性哈希把取模换成"哈希环 + 顺时针寻址"，增删节点只影响相邻区段，迁移量约 1/N。要能顺口说出"为什么是 1/N"：只有新节点逆时针到上一个节点之间的那段数据需要搬家。详见[《01-分布式理论基础》](/java-study-guide/posts/01-分布式理论基础/)

### 269.（分布式与高并发·易）一致性哈希引入"虚拟节点"主要是为了解决什么问题？

- B. 够，时间戳是毫秒级的，一毫秒内可以无限生成

### 272.（分布式与高并发·中）Redisson 的看门狗（watchdog）自动续期，在什么条件下才会生效？

- B. 只有方法上加了 @Transactional 才会生效
- C. 锁被其他线程抢占后会自动续期
- D. 加锁时没有显式指定 leaseTime 才生效，默认 30 秒过期、约每 10 秒续一次

答案：D
解析：不传 leaseTime 时 Redisson 默认给 30 秒过期，并启动后台线程按 1/3 周期（约 10 秒）检查续期，业务没执行完锁就不会失效。一旦显式传了 leaseTime，等于声明"超时我自己负责"，看门狗不再介入——业务跑超时也没人救，这是线上最常见的踩坑点。释放时配合 `isHeldByCurrentThread()` 判断，避免误删他人重新抢到的锁。详见[《01-分布式理论基础》](/java-study-guide/posts/01-分布式理论基础/)

### 273.（分布式与高并发·中）某服务用 Redis 单实例 + 主从（哨兵）实现分布式锁，以主节点写入成功为准。一次主节点宕机触发切换后，出现了两个请求同时进入扣减逻辑。原因是？
- A. 主从复制是异步的，锁还没同步到从库主节点就宕机了，切换后新主节点上根本没有这把锁
- B. 哨兵会自动删除所有带过期时间的 key
- C. 从库提升为主库后会清空全部数据
- D. SET NX 命令在主从架构下不生效

### 274.（分布式与高并发·中）用 ZooKeeper 实现公平锁时，每个客户端只监听自己前一个顺序节点的删除事件，而不是监听 /locks 下所有子节点的变化，目的是？
- A. 减少 ZK 集群的磁盘写入量
- B. 让锁支持可重入
- C. 避免羊群效应：一次释放唤醒全部等待者，绝大多数抢不到还要重新注册监听，形成无效广播
- D. 绕过 ZAB 协议过半提交的限制

答案：C
解析：如果所有人都监听父节点，每次释放锁都会唤醒全部等待者，它们抢不到锁只能重新注册，白白制造一轮惊群。只 watch 前一个节点，锁释放时恰好唤醒队首的下一个，天然形成公平队列。ZK 锁的另一优势是临时节点随会话消失，客户端宕机锁自动释放，不会死锁；代价是写要走 ZAB 过半提交，性能不如 Redis。详见[《01-分布式理论基础》](/java-study-guide/posts/01-分布式理论基础/)

### 275.（分布式与高并发·难）TCC 中的"悬挂"指的是哪种时序问题？
- A. Try 先到、Confirm 迟迟不来，资源被长期冻结
- B. Confirm 重试导致资源被重复扣减
- C. 参与方没收到 Try 却先收到 Cancel，回滚了一笔不存在的业务
- D. Cancel 先执行完，迟到的 Try 才落地并冻结资源，此后没有任何事务会再来解冻它

答案：D
解析：C 描述的是**空回滚**——Try 从未执行，Cancel 却先到，若不识别就会误改数据；D 才是**悬挂**，Cancel 已走完，迟到的 Try 又把资源冻上，这笔冻结永远不会被释放。两者都靠"事务状态表 + 幂等控制"化解：执行 Cancel 前先查/插入状态记录（区分"从未 Try"与"Try 成功"），Try 落地前也先校验状态，发现已回滚就拒绝执行。详见[《01-分布式理论基础》](/java-study-guide/posts/01-分布式理论基础/)

### 276.（分布式与高并发·难）关于"本地消息表"与"RocketMQ 事务消息"的可靠性差异，下列说法最准确的是？

- B. 本地消息表把业务写入与消息记录放在同一个本地事务里，MQ 当时不可用也不影响业务提交；事务消息依赖 Broker 回查生产者，生产者长时间不可达时消息会悬而未决

### 277.（分布式与高并发·中）某接口用固定窗口限流，阈值 100 次/秒。客户端在某一秒的最后 0.1 秒发了 100 个请求，紧接着在下一秒的前 0.1 秒又发了 100 个，全部放行。这 0.2 秒里实际通过了多少请求，说明什么？

### 278.（分布式与高并发·难）某服务调用下游的超时率从 1% 涨到 60%，平均耗时从 20ms 涨到 80ms。熔断器跳闸进入"打开"状态后，正确的后续行为是？
- A. 打开状态持续一个冷却窗口，其间请求直接快速失败；冷却结束进入半开，只放行少量探测请求，成功率恢复则关闭熔断器，否则重新打开并重新计时
- B. 打开后永久拒绝，必须人工重启服务才能恢复

### 280.（系统设计·难）承接上题，布隆过滤器的位数组长度 m 与哈希函数个数 k 需按容量 n 和目标误判率 p 推算。若 p 定为 1%，下列哪组取值最接近？
- A. m/n ≈ 4 bit，k ≈ 2
- B. m/n ≈ 9.6 bit，k ≈ 7
- C. m/n ≈ 20 bit，k ≈ 14
- D. m/n ≈ 1 bit，k ≈ 1

答案：B
解析：由 `m = -n·lnp/(ln2)²` 与 `k = (m/n)·ln2` 可得：p=1% 时约 9.6 bit/元素、k≈7；p=0.1% 时约 14.4 bit/元素。k 不是越大越好，超过最优值后位数组被置 1 的比例上升，误判率反而回升。工程上容量 n 估小了会让实际 p 迅速恶化，所以通常按预估峰值的两倍以上设计并定期重建。详见[《03-系统设计场景题》](/java-study-guide/posts/03-系统设计场景题/)

答案：A
解析：这是经典的"上界不等于紧界"：n 次 O(logn) 只是上界，实际求和是 Σ(每层节点数 × 该层高度)，收敛到 O(n)。注意逐个 insert 建堆才是 O(nlogn)，这也是堆排序整体复杂度仍为 O(nlogn) 的原因。详见[《03-算法刷题路线》](/java-study-guide/posts/03-算法刷题路线/)

### 305.（算法·中）用 `LinkedHashMap` 实现 LRU 缓存，构造器参数与需要重写的方法分别是？

### 306.（算法·难）从 n 个数中找第 K 大的元素，"维护一个大小为 K 的小顶堆"这种做法的时间复杂度是？
- A. O(nlogn)：每个元素都要进堆排一次序
- B. O(nlogK)：遍历 n 个元素，每次堆调整 O(logK)
- C. O(Klogn)：堆里始终只有 K 个元素
- D. O(n)：堆的插入删除都是常数时间

答案：B
解析：遍历是 O(n)，每次入堆/出堆是 O(logK)，合计 O(nlogK)；K 远小于 n 时明显优于整体排序的 O(nlogn)，这正是"海量数据取 Top K"的标准解。选小顶堆是为了让堆顶正好是当前第 K 大，超容量就弹掉。详见[《03-算法刷题路线》](/java-study-guide/posts/03-算法刷题路线/)

### 307.（算法·中）下面哪种二分写法在收缩区间时可能陷入死循环？
- A. 左闭右闭：`while (left <= right)`，配 `left = mid + 1` / `right = mid - 1`
- B. 左闭右开：`while (left < right)`，配 `left = mid + 1` / `right = mid`
- C. `while (left <= right)` 且 `mid = left + (right - left) / 2`
- D. `while (left < right)` 且 `mid = (left + right) / 2`，并用 `left = mid` 收缩左边界

答案：D
解析：下取整的 mid 在区间只剩两个元素时会等于 left，若还用 `left = mid` 收缩，left 永远不动就死循环。两个修法：改成 `left = mid + 1`，或把 mid 改成上取整 `(left + right + 1) / 2`——一句话，收缩方向必须和取整方向配套。详见[《03-算法刷题路线》](/java-study-guide/posts/03-算法刷题路线/)

### 391.（系统设计·中）统计 UV 时只关心去重后的数量、不关心具体是谁，用 Redis 的 ＿＿＿ 结构只需约 12KB 就能把标准误差控制在 0.81%。
答案：HyperLogLog
解析：HyperLogLog 用概率算法估算基数，内存恒定约 12KB（16384 个 6bit 寄存器），比 SET 省下几个数量级。代价是只能拿到计数、拿不到成员列表，且结果本身是近似值。判断要不要精确应先问指标的精度要求：排行榜要精确名次，UV 通常只用来看趋势。详见[《01-Redis》](/java-study-guide/posts/01-Redis/)

### 392.（系统设计·中）IM 系统为每个会话维护一个单调递增的 ＿＿＿，接收方按它排序与去重，一次解决"不乱序"和"重复消息"两个问题。

### 395.（设计模式·易）`Integer` 缓存 -128~127 与字符串常量池复用字面量，都是＿＿＿模式的落地：由工厂统一管理、共享不可变实例来节省内存。

### 396.（设计模式·中）静态内部类（Holder）单例既能延迟加载又线程安全，靠的是内部类被首次引用时才触发类加载，且 JVM 保证同一个类的＿＿＿过程只执行一次。

### 398.（算法·中）「找下一个更大元素」这一类题（每日温度、柱状图中最大的矩形）的标准解法是维护一个＿＿＿栈。

### 431.（消息队列·中）Kafka 通过分区设计保证了消息的全局有序，只要 Topic 有足够多的分区，就能同时兼顾吞吐与全局顺序。
- A. 正确
- B. 错误

答案：B
解析：Kafka 只保证分区内有序，分区之间没有任何顺序关系，所以"全局有序"与"多分区并行"本质互斥，真要全局有序只能退化成单分区。业务上的常规解法是收敛为"同一业务 key 有序"，按 key 路由到同一分区。详见[《03-Kafka》](/java-study-guide/posts/03-Kafka/)

### 432.（Redis·中）RDB 是二进制的紧凑快照，恢复速度比 AOF 快，代价是可能丢失最后一次快照之后的写入。
- A. 正确
- B. 错误

答案：A
解析：RDB 定时 fork 子进程做全量快照，文件小、加载快，但两次快照之间的写入会丢；AOF 记录写命令序列，everysec 下最多丢约 1 秒，代价是文件更大、恢复更慢。生产常用混合持久化兼顾两者。详见[《01-Redis》](/java-study-guide/posts/01-Redis/)

### 433.（消息队列·易）RabbitMQ 生产者开启 publisher confirm 后收到 Basic.Ack，只说明消息已被 Broker 接收，并不代表消费者已经处理成功。
- A. 正确
- B. 错误

答案：A
解析：Confirm 只覆盖"生产者到 Broker"这一段，与消费成功与否无关；若消息到了交换机却路由不到任何队列，还要靠 publisher-returns + ReturnCallback 才能捕获。全链路可靠需要队列与消息持久化、消费者手动 ACK、失败重试与死信队列逐段补齐。详见[《02-RabbitMQ》](/java-study-guide/posts/02-RabbitMQ/)

### 434.（Elasticsearch·中）ES 中「更新一条文档」的底层实现是直接在原 segment 里原地修改这条记录。
- A. 正确
- B. 错误

答案：B
解析：segment 一旦生成即不可修改，更新实际是「标记旧文档为删除 + 写入一条新文档」，被标记的旧文档要到段合并（merge）时才真正回收空间——这正是 ES 更新代价高的根源，也是它不适合当主库的原因之一。详见[《05-Elasticsearch》](/java-study-guide/posts/05-Elasticsearch/)

### 435.（Nginx·中）开源版 Nginx 的 upstream 只提供被动健康检查（max_fails/fail_timeout），主动探测需要商业版或第三方模块。
- A. 正确
- B. 错误

答案：A
解析：被动检查是「请求失败达到 max_fails 次就把该节点暂停 fail_timeout 时长不派流量」，属于事后发现；主动探测（定期发请求探活）开源版不具备，需要商业版或 OpenResty 等第三方模块补齐。详见[《07-Nginx》](/java-study-guide/posts/07-Nginx/)

### 436.（MongoDB·易）MongoDB 的单文档更新本身就是原子的，所以把强关联数据放进同一个文档、减少对跨文档事务的依赖，是它的惯用设计。
- A. 正确
- B. 错误

答案：A
解析：一条 BSON 文档的更新不会「写一半」，因此「把需要一起变更的数据内嵌在同一文档里」比开事务更高效，这也是文档模型的核心设计思路。MongoDB 4.0 起虽支持多文档事务，但性能与生态仍不如关系库，不适合当 MySQL 的替代品。详见[《08-MongoDB》](/java-study-guide/posts/08-MongoDB/)

### 437.（框架·中）Spring Boot 扫描到的候选自动配置类都会被注册成 Bean，条件注解只决定它们的加载先后顺序。
- A. 正确
- B. 错误

答案：B
解析：条件注解是"是否生效"的开关，不满足条件的候选类根本不会注册（@ConditionalOnMissingBean 就是让位给用户配置的关键）；加载先后顺序由 @AutoConfigureOrder/@AutoConfigureBefore 这类注解控制，与条件注解是两件事。详见[《SpringBoot实战》](/java-study-guide/posts/02-SpringBoot实战/)

### 438.（框架·难）Feign 的重试只应对幂等操作开启：对下单这类非幂等接口重试，可能造成重复下单。
- A. 正确
- B. 错误

答案：A
解析：重试的本质是"再发一次请求"，查询接口重复执行无害，下单、扣款重复执行就是事故；所以只给幂等接口配 Retryer，非幂等接口要靠超时 + 幂等号来兜底。另需显式配置 connectTimeout/readTimeout，避免下游慢调用拖垮自己。详见[《SpringCloud微服务》](/java-study-guide/posts/04-SpringCloud微服务/)

### 439.（框架·难）Sentinel 触发限流或熔断后，请求会走 blockHandler 等兜底逻辑返回降级结果，而不是把异常直接抛给用户。
- A. 正确
- B. 错误

答案：A
解析：这正是"降级"的意义：被限流/熔断/异常时返回缓存旧值、默认值这类"有损但可用"的结果。注意规则默认存在内存里，重启即丢失，生产要接 Nacos 做规则持久化。详见[《SpringCloud微服务》](/java-study-guide/posts/04-SpringCloud微服务/)

### 440.（单元测试·难）测试类上标注 @Transactional 后，用例结束时数据库、Redis 与消息队列的写入都会一起回滚，因此不会污染环境。
- A. 正确
- B. 错误

答案：B
解析：它只回滚当前事务里的数据库操作，回滚不了 Redis、消息队列等外部副作用；而且因为复用同一连接、内层事务被合并，还会掩盖事务传播行为的 bug。生产级做法是独立测试库每轮清理，或用 Testcontainers 每次起新容器。详见[《05-单元测试与工程质量》](/java-study-guide/posts/05-单元测试与工程质量/)

### 441.（认证与安全·中）JWT 的 payload 是加密的，所以把手机号等敏感信息放进 payload 是安全的。
- A. 正确
- B. 错误

答案：B
解析：JWT 是"签名"不是"加密"，header 与 payload 只是 Base64URL 编码，任何人都能解开看内容；签名只保证不被篡改，不保证保密。payload 里只放 userId、role 这类不敏感标识，手机号等敏感数据留在服务端按需查询。详见[《06-认证与安全》](/java-study-guide/posts/06-认证与安全/)

### 442.（分布式与高并发·中）一致性哈希环上移除一个节点时，该节点原本承载的数据会被平均分摊到其余所有节点上。
- A. 正确
- B. 错误

答案：B
解析：数据是沿环顺时针找到第一个节点存放的，所以被移除节点的数据只会整体交给它在环上的**顺时针后继**那一台，其余节点分毫不动。之所以看起来"分摊开了"，是因为虚拟节点让每个物理节点在环上有上百个落点，它的后继自然散布在多台机器上——这是虚拟节点的第二个好处：故障压力均摊。详见[《01-分布式理论基础》](/java-study-guide/posts/01-分布式理论基础/)

### 443.（系统设计·易）短链跳转返回 301（永久重定向）而不是 302，好处是浏览器会缓存这次跳转，从而减少对短链服务的回源请求。
- A. 正确
- B. 错误

答案：A
解析：301 会被浏览器缓存，同一短码的后续访问可能根本不打到服务端，对读多写少的短链系统是很大的减负。反过来，如果业务强依赖每次点击都回源，才会考虑 302——但点击统计的正确做法是异步上报（写 MQ 不阻塞跳转），而不是牺牲缓存来换。详见[《03-系统设计场景题》](/java-study-guide/posts/03-系统设计场景题/)

### 444.（系统设计·中）Redis ZSET 中分数相同的成员会按成员名的字典序排列，因此做排行榜时若要求"同分先达到者排前"，需要把时间信息编进 score。
- A. 正确
- B. 错误

答案：A
解析：ZSET 的排序规则是"先比 score，score 相同再按 member 字典序"，字典序与达成先后毫无关系。常规做法是把 score 设计成复合值（例如 `分数 × 10^10 + (大常数 - 时间戳)`），一次 ZADD 就把并列名次也定好；取榜单用 ZREVRANGE，查自己名次用 ZREVRANK。注意"精确名次"与"TopN 列表"是两个量级的问题，亿级数据要靠分桶 + 近似 + 定时快照。详见[《03-系统设计场景题》](/java-study-guide/posts/03-系统设计场景题/)

### 445.（工具链·易）git rebase 会把被重放的提交彻底删除，之后再也找不回来。
- A. 正确
- B. 错误

答案：B
解析：rebase 是"把提交逐个重放"，原提交仍以悬空对象留在仓库里，通过 reflog 或旧 sha 通常还能找回，直到 gc 回收；它真正危险的地方不是"丢内容"，而是改写了公共历史导致协作者本地历史错位。详见[《04-开发工具链-Git-Maven-Linux》](/java-study-guide/posts/04-开发工具链-Git-Maven-Linux/)

### 446.（设计模式·中）把 `@Scope("prototype")` 的 Bean 注入到一个单例 Bean 之后，该单例持有的始终是注入时创建的那一个实例。

- B. 错误

### 447.（算法·易）快速排序的最坏时间复杂度是 O(nlogn)。
- A. 正确
- B. 错误

答案：B
解析：快排最坏是 O(n²)——每次划分只能分出一个元素（如已有序数组固定取首元素为基准），递归深度退化成 n。O(nlogn) 是它的平均复杂度，这一点是最常见的时间复杂度误解之一。详见[《03-算法刷题路线》](/java-study-guide/posts/03-算法刷题路线/)

### 448.（算法·中）HashMap 的查询平均时间复杂度是 O(1)，最坏情况下会退化成 O(n)。
- A. 正确
- B. 错误

答案：A
解析：哈希均匀时定位到桶是常数时间；大量 key 落在同一个桶（哈希碰撞）时会退化成链表扫描，JDK 1.8 用"链表长度超过 8 且容量 ≥ 64 时转红黑树"把最坏情况改善到 O(logn)。详见[《03-集合与泛型》](/java-study-guide/posts/03-集合与泛型/)
